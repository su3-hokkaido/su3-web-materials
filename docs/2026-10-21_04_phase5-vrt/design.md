# Phase 5: Visual regression test

## Background

`docs/project_plan.md` section 11 specifies a visual regression test (VRT) with Playwright's
`toHaveScreenshot` against the built Storybook, run inside the official Playwright image so that
fonts and rendering are identical locally and in CI. Section 14 (Phase 5) schedules it after the
package build. Two follow-ups were carried over from earlier phases: tests for
`prefers-reduced-motion`, `forced-colors` and `pointer: coarse`, which need real media emulation.

## Requirements

- Every story of the built Storybook (`dist/storybook`, Phase 3) is captured in light and dark, per
  viewport (`desktop`, `mobile`), and compared with committed baselines in
  `tests/vrt/__screenshots__/{viewport}/{scope}/{storyId}-{theme}.png`.
- Stories are enumerated from each product's `index.json`; a new story needs no test code.
- `parameters.vrt` configures a story: `disable`, `viewports`, and (new) `themed`; unknown keys or
  values fail.
- A baseline without a story fails (orphan check).
- `make vrt` and `make vrt-update` run in the Playwright image (`linux/amd64`, tag equal to
  `@playwright/test`).
- Tests cover `prefers-reduced-motion`, `forced-colors` and `pointer: coarse` for the button.

## Non-goals

The GitHub Actions workflow (Phase 6), browsers other than Chromium, interaction-state screenshots
(hover, focus), README (Phase 8).

## Technical approach and key decisions

### 1. Which stories are captured (refines section 11)

Every product's Storybook contains all shared stories, differing only in the theme. Capturing them
all per product multiplies the baselines by the number of products for no new information, but
capturing them once (the original rule, "from the first product") would pick `acme` alphabetically
and lose the default look. Rule:

- Shared stories are captured from the default product `sample`, under `shared/`.
- Any other product captures only the shared stories that opt in with `parameters.vrt.themed: true`
  (stories that show a theme's effect, such as the Button `Variants` story), under `{productId}/`.
- Product-only stories are always captured under their product.

`themed` is only known at run time (index.json carries no parameters), so such tests are generated
for every product and skipped when the story does not opt in, exactly like `disable`.

### 2. Render readiness

Besides Storybook's render phase (`finished`) and `document.fonts.ready`, each screenshot waits for
`updateComplete` of every `su3-*` element, so a Lit element is never captured mid-render.

### 3. Docker

A `vrt` stage between `build` and `preview` (preview stays last so an untargeted build produces it):
`mcr.microsoft.com/playwright:v1.64.1-noble`, installing only `@playwright/test`, user `pwuser`
(uid 1001, like the GitHub runner), running `node_modules/.bin/playwright test` directly because the
image's Node.js (24) does not satisfy `devEngines` and `npx` would enforce it. The compose `vrt`
service is pinned to `linux/amd64` and behind the `vrt` profile; it mounts `package.json` (so the
config and tests are ES modules), `playwright.config.ts`, `tests/vrt`, `dist/storybook` read-only,
`test-results` and `playwright-report`. `make vrt` builds every product Storybook first and then runs
the service; `make vrt-update` adds `--update-snapshots=changed`. There is no `local-vrt`: pixels
must come from the image. The VRT is not part of `ci` (emulation on Apple Silicon is slow); Phase 6
gives it its own workflow.

### 4. Feasibility on this machine

The development machine is arm64, so the amd64 image runs under emulation. The first task proves that
Chromium starts and produces screenshots under emulation and records the time. Fallback if it proves
unreliable: baselines are generated by the Phase 6 CI runner and local `make vrt` is used on
amd64-capable hosts; this would be recorded as a limitation.

### 5. Media-feature checks

`tests/vrt/media.spec.ts` uses the same disk-served Storybook and Playwright's `emulateMedia`:

- `reducedMotion: 'reduce'`: the button's and its state layer's transition durations are 0s.
- `forcedColors: 'active'`: the text variant's transparent border resolves to a visible color, and
  the hovered border differs from the resting one.
- `pointer: coarse` (true in the `mobile` project because Pixel 7 is a touch device): the pseudo-element
  hit area is 44px tall for the medium button; on `desktop` it is absent.

A shared module `tests/vrt/site.ts` holds the origin, the disk routing, the story URL and the render
wait for both specs.

### 6. Orphan check and maintenance

As in the template: a baseline whose story no longer exists fails the run. Baselines made stale by a
removed `themed` flag or a narrowed `viewports` list cannot be detected and are deleted by hand
(`CLAUDE.md` already says so).

## Affected files and directories

- New: `playwright.config.ts`, `tests/vrt/{stories.ts,stories.test.ts,site.ts,stories.spec.ts,
media.spec.ts}`, `tests/vrt/__screenshots__/`.
- Modified: `Dockerfile`, `compose.yaml`, `Makefile`, `vitest.config.ts` (Node project includes

  (sections 11, 14, 15, 17).
- Design tokens, package `exports`, `custom-elements.json`, story titles: unchanged. README and
  README_JA: unchanged (Phase 8).

## Provenance

The configuration, helpers and spec are adapted from the owner's `su3-ui-component-catalog-template`;
the default-product rule, `themed`, the readiness wait and the media spec are new. Nothing is taken
from material-web.

## Judgment calls

- `themed` instead of capturing every shared story per product: scalable and still guards each theme.
- VRT stays out of `ci` and in its own workflow later, because of its cost and the amd64 requirement.
- The media checks live in the Playwright suite (not Vitest Browser Mode) because `pointer: coarse`
  needs a touch device context, which Playwright's project configuration provides.
